# Day 01 练习

先闭卷回答，再展开参考要点。参考答案用于校准概念，不能替代项目证据。

## E1：两分钟讲解（L01）

向一位 Java 同事解释 Agent = LLM + Harness，用“查订单”的例子说明工具调用从生成到执行的过程。

<details>
<summary>参考要点</summary>

应包含上下文装配、模型输出调用请求、运行系统校验和执行、结果回填、继续决策与终止。不能说模型直接执行了 Java 方法。公式是工程抽象，Harness 不必是单个类。

</details>

## E2：画执行轨迹（L02、L03）

假设用户发出一个问题，模型先调用查询工具、再调用计算工具，最后回复。画出事件顺序，数出模型调用次数，并解释为什么无法仅凭该描述确定框架 iteration 计数。

<details>
<summary>参考要点</summary>

在题设每次只发起一个工具调用且无重试的情况下，共三次模型调用、两次工具执行、一次用户发问。iteration 的定义与消息编码需查具体实现；工具描述是否算独立消息、多个结果怎样包装，不能凭空假定。

</details>

## E3：找到证据（L04）

在固定项目版本中查出模型调用、循环、工具执行、上下文装配、状态保存的入口。每项记录：版本/提交、文件与方法、输入输出、证据支持的结论。没有找到的写“未定位”，不要补猜测。

<details>
<summary>验收要点</summary>

五条证据必须能重新定位。框架提供某能力与项目实际启用某能力要分开；配置默认值与运行时生效值也要分开。公开记录使用脱敏说明，不上传内部源码。

</details>

## E4：失败恢复（L05）

一个“创建工单”工具成功后，进程在保存结果前退出。用户重发请求。你会在什么地方防止重复创建？还需要保存什么？

<details>
<summary>参考要点</summary>

识别业务操作而非只依赖模型生成的调用 ID；采用业务幂等键及服务端唯一约束/幂等接口；记录操作状态并能查询确认结果。超时不代表没有成功。仅把聊天记录恢复到 Memory 无法证明副作用是否发生。

</details>

## E5：纠正三句话（L01—L04）

1. “用了 ReActAgent，所以我们的权限、checkpoint 和 tracing 都做好了。”
2. “配置里是 100，所以一个会话只能聊 100 轮。”
3. “把历史消息保存下来，就可以从任意失败点继续执行。”

<details>
<summary>参考要点</summary>

逐条要求实现证据：框架能力不等于已接入；100 的单位与生效路径需核对；会话记录不等于包含副作用和执行位置的 checkpoint。

</details>
